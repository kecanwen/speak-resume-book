### 一 · 收钱吧百万商户级 C 端点餐与外卖小程序架构

<p className="meta">收钱吧 · C 端小程序 · 前端架构</p>

**项目背景：** 收钱吧扫码点餐与校园外卖小程序覆盖全国 80 万+ 异构商户，峰值日活数百万、日均 PV 千万级（单次点餐含多页面与分包访问）。由于下沉市场千元级安卓机占比高（超过 40%），且地下档口弱网普遍，随着多规格菜品、阶梯满减、充值营销等复杂能力堆叠，小程序暴露出多业务线并行研发阻塞、低端机掉帧、深层页面栈内存溢出闪退、首屏冷启动慢等底层工程难题。

#### 1. 跨业务线微模块 NPM 分发与多仓库小程序高效联调体系

- **技术难点：** 点单、校园外卖、营销、广告四条核心业务线长期共存于单体小程序仓库，代码冲突频发且发版周期相互阻塞；
- **解耦架构：** <Q id="p1-npm" level={3}>主导“基座宿主小程序 + 业务独立 NPM 子包”解耦架构</Q>。宿主小程序沉淀协议层与公共 SDK，各业务线剥离为独立 Git 仓库在私有 NPM 发布，并在构建期动态编译注入小程序分包；
- **攻克本地联调死穴：** 针对微信开发者工具对软链接（Symlink）支持缺陷导致的文件 Watch 失效与寻址崩溃，自研构建 CLI 工具。为子包提供轻量 Mock 宿主沙箱，支持单业务脱离主工程独立开发；<Q id="p1-cli" level={2}>在宿主模式下，通过构建流 Alias 劫持将 NPM 依赖无感重定向至本地源码物理监听，实现业务包改动 1 秒内触发微信开发者工具热重载</Q>，彻底打断发版阻塞。

#### 2. 小程序路由拦截与并行数据预拉取流水线

- 针对扫码点餐“代码包下载 → 基础库容器启动 → 页面 onLoad 挂载 → 发起网络请求”的传统串行瀑布流，在全局路由守卫层建立网络请求与小程序容器生命周期并行化管道（Pre-fetch Pipeline）；
- 扫码解析商户与桌号后，在页面组件编译前置提前并发拉取菜单与核心券列表，将网络往返耗时（RTT）与容器启动耗时重叠并行化，<Q id="p1-prefetch" level={3}>首屏关键满屏时间（T2）从 3.5s 压缩至 1.1s，扫码后跳失率降低 22%</Q>。

#### 3. 小程序双线程 setData 序列化通信堵塞治理

- 针对用户高频加购时，全量更新导致千元机单次 JSBridge 序列化耗时超 120ms、数据包突破 300KB 导致列表滑动掉帧的痛点，<Q id="p1-setdata" level={3}>自研基于路径 Diff 的局部更新器（Path-based Granular Setter）</Q>；
- 逻辑层维护不可变状态快照，仅向渲染层定向派发扁平化变更路径（如 `cart.items[3].qty`），并结合 16ms 帧生命周期调度器进行操作合并与批量推送；单次通信数据量由 300KB+ 降至 2KB 以内，低端机连续加购帧率稳定在 55 FPS 以上。

#### 4. 深层页面栈内存泄漏与位图内存优化

- 针对点餐“店铺列表 → 菜单 → 菜品详情 → 领券 → 订单确认”多层页面栈跳转导致的内存暴涨，封装生命周期自动化注销器，在页面 onUnload 时强制断开全局 EventBus 与跨包状态监听，阻断闭包泄漏；
- 针对商户上传菜品原图导致的位图解码内存爆炸，构建小程序端专用图片组件，结合 CDN/OSS 视口尺寸动态计算并下发降采样裁剪参数（避免 2000px 大图加载到 80px 容器中），<Q id="p1-oom" level={2}>长时间浏览内存占用降低 45%，线上 OOM 崩溃率下降 70%</Q>。

#### 5. 地下弱网环境下的 SWR 快照秒开与时序竞态控制

- 针对档口弱网，引入 Stale-While-Revalidate（SWR）机制，利用本地 `wx.setStorage` 缓存快照在 100ms 内秒开可交互菜单，后台静默差量更新最新库存与券资产；配合<Q id="p1-swr" level={2}>基于单调递增版本号的时序控制器，阻断弱网并发改单请求后发先至（Race Condition）导致的算错钱事故</Q>。

### 二 · 益丰加盟工作台与 B2B 小程序（总部—加盟商数字化）

<p className="meta">益丰 · 2026.4 至今 · 全栈（Java + 小程序 BFF）</p>

**项目背景：** 益丰以 **微信小程序** 作为加盟商主载体，承载「加盟工作台」与 B2B 订货/经营能力。使用者横跨加盟商法人、门店店长、店员、总部督导与区域经理等角色，数据按加盟商/门店/人员多级隔离。后端需在 Java / Spring Boot 体系下统一编排 **加盟人事、授信、财务、请货、供应链** 等存量系统，并接入 **大数据** 产出可下钻的经营报表；**B2B 加盟商城** 叠加合同价、授信额度、起订量、批次与营销毛利等规则，是本项目的核心复杂度。本人负责工作台后端领域建模、权限域、聚合查询与跨系统编排，并对小程序侧契约与联调闭环。**不涉及** Agent / 脚手架等研发工具链（见项目三）。

#### 1. 小程序载体与后端分层

- 工作台壳层负责登录、租户上下文、菜单与权限下发；请货、报表、商城等能力以分包 + 独立 BFF 接入，避免单体 Controller 膨胀；
- 对外统一 REST / 少量 GraphQL 聚合接口，对内按域划分 Service；<Q id="p2-mp-bff" level={1}>小程序只消费 BFF 聚合结果，跨系统字段在服务端拼装，减少端侧串行多次请求</Q>。

#### 2. 多角色、多组织权限与数据隔离

- 身份来自加盟人事域（人员、岗位、所属门店/加盟商），登录后签发带 `tenant_id`、`store_ids`、`role_codes` 的 Token；
- <Q id="p2-rbac" level={3}>采用 RBAC（角色—菜单—接口）叠加数据权限（加盟商 / 门店 / 本人）：MyBatis 拦截器与 SpEL 注解按上下文自动拼接数据范围，总部督导可按区域看到下辖门店，店员仅本人单据</Q>；
- 越权访问统一返回脱敏错误码，审计日志记录「谁看了哪家店的数据」，满足内控抽查。

#### 3. 大数据加盟商经营报表

- 明细数据留在业务库与数仓 ODS；报表指标（销售、库存周转、毛利、品类结构、同比环比）由大数据离线/近实时任务产出，写入 **ADS 指标表** 或 OLAP 引擎；
- <Q id="p2-bi" level={3}>后端提供「指标目录 + 查询 DSL + 异步导出」：按角色裁剪可见指标与门店维度，大数据只负责算，工作台负责鉴权、分页下钻与小程序图表数据整形</Q>；
- 重查询走异步任务 + 消息通知下载，避免弱网门店打开报表超时。

#### 4. 三方域接口编排（人事 / 授信 / 财务 / 请货 / 供应链）

- 各域接口差异大（SOAP/REST、不同鉴权与幂等），在加盟侧建设 **防腐层 Adapter + 统一错误码映射**；
- <Q id="p2-integrate" level={3}>典型编排：请货单创建 → 调供应链校期与批次 → 调授信占用额度 → 财务预占应付 → 人事校验门店闭店状态；失败按步骤补偿或挂起人工处理，关键链路用 RocketMQ 事件与 Outbox 保证最终一致</Q>；
- 授信域控制「能不能买」；财务域回写回款与对账单；人事域驱动人员/门店主数据同步，避免工作台自维护两套组织树。

#### 5. B2B 加盟商城（订货与营销叠加）

- **商品与价套：** 合同价、区域价、阶梯价、慢病/医保限价等多价源合并，下单时重新计价并快照留痕；
- **授信与起订：** 加购校验可用额度、账期、SKU 起订量与箱规；超授信拦截并引导还款或临时提额（回调授信域）；
- <Q id="p2-mall" level={3}>购物车支持多仓、多供应商拆单；营销券/满减与 B2B 批发价叠加时走毛利风控链，负毛利或低于总部红线直接 BizException；提交后拆成请货单 + 供应链预占 + 补贴分摊（若活动参与）</Q>；
- **批次与合规：** 冷链、特管药、处方品类等按供应链返回的可售范围过滤，门店资质（人事/证照）失效时禁止订购对应类目。

#### 6. 稳定性与可观测

- 核心接口限流、熔断与降级（报表降级为昨日汇总、商城只读目录）；
- 跨系统 TraceId 贯通，便于从小程序报错定位到某次授信/财务回调失败。

### 三 · 加盟数字化研发底座（支撑全栈交付 · AI 辅助工程化）

<p className="meta">益丰 · 2026.4 至今 · 研发效能 · 为项目二配套</p>

**项目背景：** 项目二业务迭代快、团队以 Java 为主，需要让后端能稳定交付小程序页面并控制质量。本人搭建加盟侧**研发底座**：脚手架与 OpenAPI 契约联调（全栈协作主轴），辅以 Agent、视觉回归、E2E 与可观测性。**不展开**授信/报表/五域等业务规则（见项目二）。

#### 1. 前端 Agent 工作流（Spec → 实现 → 自测 → 联调）

- 定义加盟前端的固定研发阶段：从需求/Figma 节点解析、按模板生成页面骨架、挂载接口契约、触发单测/快照、到提 PR 前的视觉回归与契约校验，全部由**可编排的 Agent 流水线**衔接；
- <Q id="p3-agent-flow" level={2}>人机分工上，Agent 负责重复劳动（脚手架、类型、Mock、用例草稿、变更影响分析），人只做业务规则、异常流和评审</Q>；

#### 2. Figma 设计稿还原与视觉回归（像素级比对）

- 建立「设计 Token → 组件库 → 页面」单向约束，页面样式优先引用设计系统变量，减少硬编码；
- CI 中对关键页面做**网页截图 vs Figma 导出稿**的图像 diff：先做布局对齐与字体/色值校验，再对差异区域做结构化报告（偏移、字号、色值 ΔE），<Q id="p3-figma-diff" level={2}>对营销与表单类页面将「肉眼对稿」改为可量化门禁</Q>；
- 对动态数据区域（列表、图表）采用遮罩/占位策略，避免误报。

#### 3. 面向「后端转全栈」的前端脚手架

- Monorepo + 约定式目录：页面、接口层、表单 Schema、权限与租户上下文分层，<Q id="p3-scaffold" level={3}>新同学按 `pnpm gen:page` 生成带类型的列表/详情/向导模板，默认接上错误处理、Loading 与空态</Q>；
- 内置 React Query / 请求封装、租户 ID 透传、与 Java 后端统一的错误码映射表，后端同事主要写 Service 对接与字段映射，不必从零学路由和状态管理；
- 文档与 ESLint 规则内嵌「推荐写法」，PR 模板强制检查接口类型是否与 OpenAPI 一致。

#### 4. 前端自测 Agent（存量代码自动补测试）

- 针对加盟仓库内的组件与 hooks，<Q id="p3-test-agent" level={2}>自测 Agent 读取源码与相邻用例风格，生成 Vitest + Testing Library 单测及关键交互用例草稿</Q>，人审后入库；
- 对表单与规则引擎页面，自动生成边界用例清单（空值、越权租户、毛利拦截失败态等），与业务测试用例互补；
- 与视觉回归、契约测试共用「变更影响面」输入，接口或组件改动时只跑相关子集，控制 CI 时长。

#### 5. 前后端联调：接口契约变更驱动前端同步

- 以 OpenAPI / 内部契约仓库为单一事实来源，后端 MR 变更契约时触发流水线：<Q id="p3-api-sync" level={2}>自动刷新前端 TypeScript 类型、API Client，并对引用该接口的页面/Store 发起 Codemod 或 Agent 补丁，生成待审 PR</Q>；
- 对破坏性变更（字段删除、枚举收缩）阻断合并，直到前端适配 MR 关联通过；
- 本地 dev 支持契约 Mock 与联调环境一键切换，减少「等后端部署才能调页面」的空转。

#### 6. 小程序在 Chromium 内跑 E2E（wxa-runner 思路选型集成）

- 市面常见 uni-app / Taro 转 H5 往往丢失原生 API、页面栈与生命周期语义；选型上倾向「浏览器载入官方编译链与基础库、模拟双线程」路线，而非业务代码转译成残缺 H5；
- <Q id="p3-wxa-runner" level={3}>曾基于 wxa-runner 思路，在加盟 CI 落地「小程序在 Chromium 内跑 E2E」：负责选型论证、内网构建与 Playwright 流水线封装（当时依赖上游 npm 包；项目现已无法从 GitHub 获取）</Q>；
- 上游不可维护后，由团队维护兼容层 / 替换方案，继续保障核心链路回归；业务包可在 Chrome DevTools 调试、Playwright 用标准选择器做端到端，规避开发者工具难以 CI 化的问题；
- 加盟小程序核心链路（登录、请货、营销配置）纳入 nightly 回归，与 H5 工作台共用一部分用例描述。
